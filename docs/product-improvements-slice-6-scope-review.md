## Purpose and boundary

This review inventories the existing create, read, update, archive, Trash, restore, and permanent-purge behavior across the API, Web, and Flutter. It identifies verification questions and possible gaps; it does not authorize implementation, endpoint additions, schema changes, or lifecycle-policy changes.

The approved CRUD scope is the user-facing resource list and exclusions in `product-improvements-crud-scope.md`. Audit/activity history, credentials, junction rows, generated records, notifications, and retained content are not general-purpose CRUD records. Preserve archive, recoverable Trash, and retention purge as distinct lifecycle operations.

## Lifecycle and data-integrity observations

- Project archive is separate from Trash. Archive is restorable without the 30-day project Trash deadline; Trash is recoverable for 30 days.
- The `DeletedContentPurger` runs on a six-hour interval and purges expired project/task/comment/attachment content. It also removes task assignment events when their tasks or projects are purged. The current worker pauses purging when Cloudinary is not configured; verify operational configuration before production rollout.
- Task and subtask deletion use soft-delete/Trash; restore is limited to the retention window and requires an active, eligible project manager or team lead on an active project.
- Project Trash listing is authorization-filtered and capped at 200 combined items. Archived/trashed project content is excluded from some child-resource Trash listings; client presentation should be checked against these exact server rules.
- Slice 1 and Slice 3 safeguards cover active-manager retention, owner transfer, guest restrictions, eligible assignees, explicit task-resolution preview/confirmation, atomic organization deactivation, and append-only assignment history. Slice 6 verification must test these protections through existing lifecycle entry points, not redefine them.
- No schema change is justified by this read-only inventory. If a verified, approved requirement cannot be met with the existing routes/data model, document the smallest additive API/schema proposal and return it for separate approval.

## Verification gaps and questions

These items are not implementation authorization:

1. **Client parity:** Static inspection shows lifecycle controls, but does not establish parity for all roles, error states, refresh behavior, and accessible entry points. Verify each accepted action in both clients.
2. **Member-removal flow:** Confirm Web and Flutter use preview plus confirmation with `snapshotHash` and explicit per-task resolutions, including organization-wide deactivation. Confirm stale preview and limit errors are shown without partial-success UI.
3. **Task detail retrieval:** There is no standalone task GET route. Verify all supported navigation paths can load task details and document any actual unreachable entry point before proposing an API addition.
4. **Subtask delete semantics:** The route is `DELETE`, while the approved lifecycle model expects reversible Trash where content is recoverable. Verify the implementation and UI wording; do not change it based on the verb alone.
5. **Organization CRUD:** Organization profile update/delete are absent. Decide whether they are needed; hard delete must not be inferred because organizations own projects and history.
6. **Comments and notifications:** Comment update and notification dismissal are absent and remain explicit product decisions under the CRUD scope proposal.
7. **Permanent purge operations:** Verify child ordering, assignment-history deletion, Cloudinary cleanup, retry behavior, and tenant-scoped visibility using disposable fixtures. Do not run a purge against production data as part of this review.
8. **Authorization matrix:** Exercise owner/admin/project-manager/team-lead/contributor/viewer/guest and inactive/suspended cases for the existing lifecycle operations; confirm cross-tenant IDs never expose records.
